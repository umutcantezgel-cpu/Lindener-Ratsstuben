# Security Audit und Threat Model (SECURITY-PHASE-01)

## [SECTION:SECURITY-BASELINE]
- **Git Repo:** Es existiert kein aktives lokales `.git` Repository. Ein Git History Leak-Scan war daher negativ.
- **Environment:** Es werden keine sensitiven Umgebungsvariablen wie Tokens oder Private Keys im Code hartkodiert oder in production mit Client-Bundles geleakt.
- **Zustand:** Basis-Security verifiziert, jedoch OWASP Abhängigkeitswarnungen vorhanden.

## [SECTION:OWASP-AUDIT]
- **A01 Broken Access Control**: Anwendung besitzt derzeit keine sensiblen Admin-Routen, die durch Auth gesperrt werden müssen. Die einzige Ausnahme sind evtl. API Routen, die auf interne Systeme zugreifen könnten (zZt. nicht gegeben).
- **A03 Injection**: Alle User-Inputs stammen von `ContactForm` und werden client-seitig validiert, dann per Formspree geshippt. Keine direkte DB-Injection möglich.
- **A05 Security Misconfiguration**: Einige Third-Party Dependencies weisen High-Severities auf (Next.js, Minimatch, Glob).
- **A06 Vulnerable Components**: `npm audit` identifizierte 8 Vulnerabilities, darunter 6 High. Details siehe Dependency Scan.
- **A07 Authentication Failures**: Nicht zutreffend (kein eigener Auth-Layer).
- **A09 Logging Failures**: Client und Server loggen Monitoring Analytics in `/api/monitoring/`. Es muss bedacht werden, keine PII im Logger aufzubewahren.

## [SECTION:ATTACK-SURFACE]
- Formulare: `ContactForm.tsx` (externe API: Formspree).
- API-Routen (alle GET/POST in `src/app/api/monitoring/*`).
- Client-Side Speicher: localStorage wird rudimentär geprüft in CookieBanner.
- Dynamische Parameter: Keine kritischen unvalidierten URL Inputs.

## [SECTION:THREAT-MODEL] (STRIDE)
1. **API Monitoring Routen (`/api/monitoring/errors` etc.)**
   - **Spoofing**: Nicht anwendbar.
   - **Tampering**: User könnten Fake Error Reports absenden, um den Log zu verschmutzen.
   - **Denial of Service (D)**: Hohes Risiko. Ein Angreifer könnte die Routen fluten und serverseitige Ressourcen lahmlegen.
2. **Contact Form**
   - **Tampering**: XSS-Payloads in Input-Feldern. Formspree übernimmt zum Teil Sanitisierung, aber Client-Replikation verwendet strikt Reacts JSX Escaping.
   - **DoS**: Abuse der Formularstrecke zum Spammen.

## [SECTION:DEPENDENCY-SCAN]
Die `npm audit` Prüfung ergab 8 Treffer:
- **`glob`, `minimatch`, `picomatch` (High, ReDoS)**: Fix bedarf Dependency Overrides.
- **`next` (High, DoS/Smuggling)**: Vulnerability in `<15.5.10`. Version 15.5.13+ dringend empfohlen.

## [SECTION:SECRET-AUDIT]
- **Env-Variablen:** `NEXT_PUBLIC_FORMSPREE_ID` ist öffentlich. Keine DB-Strings gesichtet.
- **Hardcoded Credentials:** Regex Scan nach API Keys, JWTs, Connection Strings ergab keine Treffer.
## [SECTION:SECURITY-HEADERS]
- **HSTS:** Strict-Transport-Security via next.config.mjs konfiguriert (`max-age=63072000; includeSubDomains; preload`).
- **X-Content-Type-Options:** nosniff gesetzt.
- **X-Frame-Options:** DENY gesetzt.
- **Referrer-Policy:** strict-origin-when-cross-origin.
- **Permissions-Policy:** Für sensible APIs geblockt (`camera=()`, etc.).
- **COOP / CORP:** Cross-Origin-Opener-Policy und Cross-Origin-Resource-Policy sind auf `same-origin` fixiert worden, um Spectre-artige Isolation zu gewährleisten, ohne Third-Party-Ressourcen wie Calendly zu stören.

## [SECTION:CSP-POLICY]
- **Content-Security-Policy:** Sehr strikte Architektur mit `default-src 'self'`.
- Analytics, Web-Vitals und Formspree Endpunkte sind explizit als white-listed über `connect-src` aufgenommen. Calendly Scripte/Iframes sind über `script-src` und `frame-src` authorisiert. Die CSP forciert keine Hash-Validation (`unsafe-inline`), da Next.js Hydration diverse Inline-Styles in der App Router Architektur verwendet.

## [SECTION:CORS-POLICY]
- Da API-Routes alle App-intern (`/api/monitoring/*`) via Formulare geroutet werden, ist kein expliziter CORS `Access-Control-Allow-Origin` Wildcard Header vorhanden. Alle Anfragen unterliegen `same-origin`.
- Ein API **Rate Limiting** In-Memory Mechanismus (max. 50-100 Requests/min) wurde für alle `/api/*` Mutations-Endpunkte entworfen (`checkRateLimit()`), der DoS Attacken blockiert (`HTTP 429`).

## [SECTION:INPUT-VALIDATION]
- **ContactForm.tsx**: `zod`-Schema definiert strenge Grenzen für `name` (min: 2), `email`, `subject`, `message` und sichert den Output via `react-hook-form`.
- **Reservation/PageClient.tsx**: Komplett auf `zod` (`reservationSchema`) und `react-hook-form` refaktorisiert. Felder haben strenge String/Length Constraints.
- Alle URL-Parameter in der App Router Hierarchie sind statisch oder verwenden explizit verdeckte State-Konstrukte (keine Wildcard Injection Vektoren wie `[slug].tsx`).

## [SECTION:XSS-AUDIT]
- **Output Encoding:** Da React DOM standardmäßig sanitized, sind keine ungefilterten Render-Fragmente vorhanden.
- **dangerouslySetInnerHTML:** Kommt systemweit ausschließlich für `application/ld+json` Script-Injektion via `JSON.stringify(schema)` in `JsonLd.tsx` und `SnippetAnswer.tsx` vor. Dies gilt als isoliert und entbehrt DOMPurify, da kein Payload in den Render-Tree wandert.
- **Eval/Execution:** Weder `eval()` noch `new Function()` in der Codebase gefunden.

## [SECTION:CSRF-STATUS]
- Formulare verarbeiten Mutationen via Formspree. SameSite Cookies und das Cross-Origin Post Pattern verhindern typische CSRF Hijackings der Session (die ohnehin nicht persistent auf Auth-Level ist).
- Alle Formulare (Kontakt und Reservierung) sind durch ein `_gotcha` Honeypot Feld Spam-resistent gestaltet.
